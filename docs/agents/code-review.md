# Code review

agent 對這個 repo 的 PR 做 code review 時，照這份規則決定哪些要留言、留成哪一級。review 只留言，不改程式、不 push、不 approve、不 merge。

目的：紅色留言會被當成「合併前一定要修」，所以只有真的值得修的才標紅，其餘不要讓人什麼都修。

## 三級

### 🔴 必修（擋住合併）

**兩個條件都要成立：**

1. **寫得出具體的重現路徑：** 什麼輸入或狀態、經過哪些步驟、得到什麼錯誤結果。只說「可能有 race」「這裡不太安全」不算。
2. **屬於下面其中一類：**
   - **資安與隱私：** 疑似機密沒遮罩就寫進狀態回報（明碼存在本機，也會顯示在其他 Session）、指令注入、刪到不屬於 switchboard 的檔案。
   - **資料遺失：** 誤刪其他 Session 的狀態回報、使用者的設定被蓋掉。
   - **核心承諾被打破：** 等你計數算錯；看不到狀態卻顯示「沒有在等你」；打開按鈕消失而且回不來；按鈕顯示舊的計數（ADR-0006：舊的計數比沒有計數更糟）。
   - **退化：** 這個 PR 之前正常的功能壞了；`claude plugin test agens-view` 失敗或時好時壞；`claude plugin validate` 不過。
   - **違反 repo 自己的規則：** `docs/adr/`、`GLOSSARY.md`、`AGENTS.md`，例如版本號規則（`docs/agents/versioning.md`），或使用者看得到的文字沒有五種語言都加進 `agens-view/hooks/i18n.ts`。

### 🟡 建議（留言，不擋）

- 命名、風格、小幅重構、使用者感覺不到的效能。
- 重現路徑需要極端的時序，而且結果偏保守：例如誤顯示「看不到狀態」，而不是誤顯示「沒有在等你」。
- 修法的代價比問題大：例如為了防一個罕見的 race 把所有寫入排成佇列，一次寫入卡住就會讓所有 hook 一起卡住。留言時寫出這個取捨。

### 不留言

- **這個 PR 沒動到的既有問題：** 在摘要裡列一行，建議另開 ticket（`.scratch/<feature>/issues/`），不要擋這個 PR。
- **沒有重現路徑的猜測。**
- **只能在 Mac 真機上確認的事**（osascript 的錯誤碼、終端機實際的寬度、引擎的行為）：在摘要裡列成「待真機確認」。

## 留言的寫法

- 每次 review 最多 **5 則 🔴**，挑最嚴重的。多出來的降級或寫進摘要。
- 每則 🔴 都要有：
  - **重現路徑：** 輸入或狀態 → 步驟 → 錯誤結果。
  - **建議的修法：** 一兩句，能附上要改的程式或測試更好。
- 🟡 開頭標「（建議）」，一句話說明就好。
- 留言放在對應的行上（inline comment）。摘要只寫一段：
  - 有幾則 🔴、幾則 🟡
  - 不擋的既有問題
  - 待真機確認的事項
- 語言用繁體中文，術語照 `GLOSSARY.md`。

## 驗證

留言前自己確認：

- 在 PR 的 head 上跑 `claude plugin test agens-view` 和 `claude plugin validate agens-view`。失敗就是 🔴，附上失敗的測試名稱。
- 🔴 的重現路徑，能用 `agens-view/tests/world.ts` 的假世界寫成會失敗的測試，就在留言裡附上測試的寫法。寫不出測試的，說明原因（例如測試工具觸發不了 `ui.close`）。
